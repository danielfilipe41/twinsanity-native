# Building for the web (wasm32)

`PLATFORM=web` builds the game as wasm32 on the platform layer it shares with the Linux port, with both renderer blob
sets (WebGL and WebGPU) checked in, and `ninja game` links it into a page: `build/web/game.html`, `game.js` and
`game.wasm`. The page takes the player's own disc image, reads it while the game runs, and keeps saves and settings in
the browser. Shared requirements: [BUILDING.md](BUILDING.md).

What exists:

- `PLATFORM=web python3 configure.py` writes a wasm32 build with the emsdk's `em++`, on the same `src/platform/sdl3` layer
  over the null stubs, and `ninja compile` is its check that every TU compiles for wasm32. Emscripten 4.x or newer; the
  emsdk can live beside the tree as `.emsdk` (which `.gitignore` leaves out), sourced with
  `source .emsdk/emsdk_env.sh`.
- The renderers are `webgl` (bgfx's GL ES renderer, GLSL ES 300) and `webgpu` (WGSL), both blob sets generated by
  `tools/build_shaders.py --platform web` and checked in.
- `DATA=runtime` compiles for wasm32 too: the loader, the symbol map's headers and the code-pointer table are portable C++,
  and nothing of the disc's data is in the build.

What a link needs:

1. bgfx, bx and bimg built for wasm: `BGFX_WEB_PREFIX` names where `libbgfxRelease.a` and the rest land
   (`third_party/bgfx/.build/wasm32-emscripten/bin` by default). This bgfx checkout's `makefile` carries no web target and
   no GENie binary, so its `gmake-web` project has to be generated first.
2. The retail data as wasm. `DATA=runtime` needs the image's symbols to sit at their retail offsets inside one block, which
   is what `build/host/runtime/retail_data_symbols.s` does with `.set name, __retail_image + offset`: GNU as accepts that,
   the wasm assembler does not (no `.bss` directive, no symbol assignments with an addend). A wasm build needs the data
   symbols defined another way -- real objects per symbol, filled by the loader from the disc, with the pointers relocated
   the same way -- before the link can resolve them.
3. The page itself. It is a separate container, not something the game opens from inside `disc/`: it offers the data folder
   (or the disc image), hands it to Emscripten's file system, then runs the build. `Platform::GameData::Locate` already
   returns straight away on Emscripten, because the page provides the files.

```sh
source .emsdk/emsdk_env.sh
DATA=runtime PLATFORM=web python3 configure.py
ninja game
```

That writes `build/web/game.html`. Opening it over `file://` gives the picker, which copies a chosen image into the
page's file system; a page served over HTTP reads its image with Range requests instead, so the browser holds only the
chunks the game is using rather than the whole image.

## Hosting it

The page looks for `disc.iso` or `disc.bin` beside itself and starts the game with the image it finds, so a site needs
just this build and one image:

```sh
DATA=runtime PLATFORM=web python3 configure.py && ninja game
python3 tools/web_host.py --iso ~/Documents/game.iso
# play at http://localhost:8765/game.html
```

`tools/web_host.py` serves the build and answers Range requests for the image wherever it lives, with the content types
a browser needs (`game.wasm` as `application/wasm`, no caching of the page and module). Any static host works as well
when it answers Range requests -- nginx, Apache and `python3 -m http.server` all do -- as long as `.wasm` is served as
`application/wasm`. `/game.html?disc=<url>` points the page at an image anywhere the site serves, and a server without
Range support falls back to downloading the image whole.

Saves and settings live in the page's IndexedDB mount of `~/.local/share/twinsanity`, so they are per browser and per
site origin, and survive a reload.
