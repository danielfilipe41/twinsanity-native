# Building for the web (wasm32)

`PLATFORM=web` builds the game as wasm32 on the platform layer it shares with the Linux port, with both renderer blob
sets (WebGL and WebGPU) checked in, and `ninja game` links it into a page: `build/web/game.html`, `game.js` and
`game.wasm`. The page takes the player's own disc image, reads it while the game runs, and keeps saves and settings in
the browser. Shared requirements: [BUILDING.md](BUILDING.md).

What exists:

- `PLATFORM=web python3 configure.py` writes a wasm32 build with the emsdk's `em++`, on the same `src/platform/sdl3` layer
  over the null stubs, and `ninja compile` is its check that every TU compiles for wasm32. Emscripten 4.x or newer; the
  emsdk can live beside the tree as `.emsdk` (which `.gitignore` leaves out), sourced with
  `source .emsdk/emsdk_env.sh`.
- The renderers are `webgl` (bgfx's GL ES renderer, GLSL ES 300) and `webgpu` (WGSL), both blob sets generated by
  `tools/build_shaders.py --platform web` and checked in. A run picks one with `?renderer=webgpu` (or `?renderer=webgl`) in
  the page's URL: the page passes it as `--renderer`, which the build takes as `TWINSANITY_RENDERER`. With no `?renderer=`
  it starts WebGL. `?stats` next to it puts the frame's numbers in the log, so the two renderers compare on the same scene.
  `webgpu` needs the `WEBGPU=1` build (below): a default build carries the WGSL blobs but not the Asyncify the renderer
  waits with, so it is the one that runs in any browser. The published page is that default build.
- `DATA=runtime` compiles for wasm32 too: the loader, the symbol map's headers and the code-pointer table are portable C++,
  and nothing of the disc's data is in the build.

What a link needs:

1. bgfx, bx and bimg built for wasm, with the WebGPU renderer in them: `BGFX_WEB_PREFIX` names where `libbgfxRelease.a`
   and the rest land (`third_party/bgfx/.build/wasm/bin` by default). This bgfx checkout's `makefile` carries no web target
   and no GENie binary, so its `gmake-web` project has to be generated first:

   ```sh
   make -C third_party/bgfx .build/projects/gmake-wasm   # needs genie on PATH, or run it once from a checkout that has one
   make -C third_party/bgfx/.build/projects/gmake-wasm EMSCRIPTEN=<emcc's directory> config=release \
        CPPFLAGS="-DBGFX_CONFIG_RENDERER_WEBGPU=1 -DBGFX_CONFIG_RENDERER_OPENGLES=30" \
        bgfx bimg bimg_decode bx
   ```

   bgfx's own default leaves the WebGPU renderer out of an Emscripten build (`src/config.h` has that platform's line
   commented out), so the renderer is switched on from the command line and no file of the submodule is edited. The
   `BGFX_CONFIG_RENDERER_*` defaults are `#ifndef` blocks that only apply when none is defined: naming one turns the whole
   default set off, which is why `WEBGPU` comes with `OPENGLES` (the version number is that renderer's, 30 for WebGL 2).
   Without them the library has no `webgpu` renderer and a build that asks for one fails at init. A checkout without the
   defines, the CI page's included, still has WebGL, which is all the published page needs.

2. `WEBGPU=1` for a build that can run it: bgfx waits on the browser through `wgpuInstanceWaitAny` -- at start-up for the
   adapter and the device, and once a frame for the GPU timer's readback -- and the WebGPU port only offers that to a
   module that can suspend, so that link adds `-sASYNCIFY`. It cannot be `-sJSPI`: JSPI may only suspend inside a promising
   call, and the page's frames arrive through `emscripten_set_main_loop`'s callback, which is not one, so a JSPI build
   stops dead on the second frame. Asyncify rewrites the module (about half again the size, and slower) but can suspend
   anywhere, which is what bgfx's Emscripten paths are written for (`emscripten_has_asyncify`). That cost is why the flag is
   not the default: every other build, the published page included, runs WebGL and needs none of it. Build both renderers
   into the one `WEBGPU=1` module (`?renderer=webgpu` and `?renderer=webgl`) so a comparison pays the same Asyncify price
   on both sides.

   ```sh
   DATA=runtime WEBGPU=1 PLATFORM=web python3 configure.py && ninja game
   # play at http://localhost:8765/game.html?stats&renderer=webgpu
   ```
3. The retail data as wasm. `DATA=runtime` needs the image's symbols to sit at their retail offsets inside one block, which
   is what `build/host/runtime/retail_data_symbols.s` does with `.set name, __retail_image + offset`: GNU as accepts that,
   the wasm assembler does not (no `.bss` directive, no symbol assignments with an addend). A wasm build needs the data
   symbols defined another way -- real objects per symbol, filled by the loader from the disc, with the pointers relocated
   the same way -- before the link can resolve them.
4. The page itself. It is a separate container, not something the game opens from inside `disc/`: it offers the data folder
   (or the disc image), hands it to Emscripten's file system, then runs the build. `Platform::GameData::Locate` already
   returns straight away on Emscripten, because the page provides the files.

```sh
source .emsdk/emsdk_env.sh
DATA=runtime PLATFORM=web python3 configure.py
ninja game
```

That writes `build/web/game.html`. Opening it over `file://` gives the picker, which copies a chosen image into the
page's file system; a page served over HTTP reads its image with Range requests instead, so the browser holds only the
chunks the game is using rather than the whole image.

## Hosting it

The page looks for `disc.iso` or `disc.bin` beside itself and starts the game with the image it finds, so a site needs
just this build and one image:

```sh
DATA=runtime PLATFORM=web python3 configure.py && ninja game
python3 tools/web_host.py --iso ~/Documents/game.iso
# play at http://localhost:8765/game.html
```

`tools/web_host.py` serves the build and answers Range requests for the image wherever it lives, with the content types
a browser needs (`game.wasm` as `application/wasm`, no caching of the page and module). Any static host works as well
when it answers Range requests -- nginx, Apache and `python3 -m http.server` all do -- as long as `.wasm` is served as
`application/wasm`. `/game.html?disc=<url>` points the page at an image anywhere the site serves, and a server without
Range support falls back to downloading the image whole.

Saves and settings live in the page's IndexedDB mount of `~/.local/share/twinsanity`, so they are per browser and per
site origin, and survive a reload.

## GitHub Pages

A site is the build's files with `game.html` as `index.html`: the module and its wasm, the page's own Montserrat and its
licence, and nothing else. In particular no disc image and no `SLES_525.68`, which the repository never carries and the
page never needs: a visitor hands it their own image, and, when it is an image of another region, the European release's
`SLES_525.68` in the page's second picker (passed to the game as `--exe`). `tools/publish_web.py` writes that site to
`build/site` and, with `--push`, makes it the `gh-pages` branch (a history of its own, so no source file is ever on the
site) and pushes it:

```sh
DATA=runtime PLATFORM=web python3 configure.py && ninja game
python3 tools/publish_web.py --push
```

`.github/workflows/pages.yml` does the same on a push that touches the page (and on demand from the Actions tab): it
installs the emsdk, generates and builds bgfx for wasm32, builds the page and runs the script. The page is published the
same way locally and from CI, so there is one thing to get right.

Then in the repository on GitHub: **Settings**, **Pages**, **Build and deployment**, source **Deploy from a branch**,
branch **gh-pages**, folder **/ (root)**. The page is then at `https://<user>.github.io/<repo>/` (the script prints the
address it works out from `origin`); the first deployment takes a minute or two.

The script copies those files by name rather than the build folder wholesale, because a disc image usually sits beside
the build (`build/web/pal.iso` is a symlink to the real one on a development machine) and a copy of the folder would
publish it. It also refuses a file near Pages' 100 MB limit and anything named like the disc.

What a visitor gets: the page asks for their own image, reads it in the tab and never uploads it. The picker path keeps
the whole image in the module's memory (~2.4 GB of the 4 GB the module addresses), so the page takes the image's size in
one allocation before reading it -- growing a file system file by copying costs twice its size for a moment, which a
full disc does not fit in. A hosted image (`?disc=<url>`) is read a chunk at a time instead when the host answers Range
requests, and needs no memory for the image.

Pages serves `.wasm` as `application/wasm`, which is what the module asks for. It needs no cross-origin isolation: this
build has no threads and no `SharedArrayBuffer`.
